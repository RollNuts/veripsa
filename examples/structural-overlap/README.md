# A clean Git merge can still need structural review

This free, local example puts four observations next to each other:

1. the result of merging two real synthetic Git branches;
2. Core's existing static file-relationship evidence;
3. historical file pairs from the existing Co-change producer;
4. the result of executing each change alone and then together.

It needs a POSIX environment with Git and Python 3.12. The private Git shim uses
`/bin/sh`; this change was verified locally on macOS. Windows is not verified. No added Python packages, account, database,
network call, model, or hosted App is used when running it. The hosted service
remains suspended. The fixtures are invented code generated into disposable
temporary repositories; your current checkout is not merged or edited.

## Run

From the repository root:

```sh
python3.12 examples/structural-overlap/demo.py
```

To save the JSON or choose an installed Git binary:

```sh
python3.12 examples/structural-overlap/demo.py > structural-demo.json
python3.12 examples/structural-overlap/demo.py --git /path/to/git
```

The output is [expected-output.json](expected-output.json), generated by an
actual run. A self-check exits nonzero if the observed matrix differs from the
expected one. Setup failures produce a bounded error, not a successful report.
The focused CI test also compares the real report with this committed output.

## What happens

The common base defines `calculate_total(amount, fee=5)`. Its caller uses
`calculate_total(100, fee=5)` in another file.

- Change A makes `fee` keyword-only. The original caller still works.
- Change B passes `fee` positionally. The original function still accepts it.
- Git merges the different files cleanly. The combined call raises `TypeError`.

Core's common-base graph already links the two files through the import and
call. The demo takes each branch's real changed-file list from Git, intersects
it with that existing graph, and shows the shared review point. It does **not**
predict the `TypeError`: the separate Python execution observes that outcome.

The cases include the counterexamples needed to interpret the signal:

| Case | Each branch | Git | Code graph | Co-change | Combined run |
| --- | --- | --- | --- | --- | --- |
| `function_contract` | Pass | Clean | Observed | Not observed | TypeError |
| `compatible_related` | Pass | Clean | Observed | Observed | Pass, 205 |
| `unrelated` | Pass | Clean | Not observed | Observed | Pass, 105 |
| `dynamic_lookup` | Pass | Clean | Not observed | Observed | TypeError |

The first case has only its initial commit. Its new call-contract mismatch has
static evidence but cannot meet the existing history support floor. The other
cases add five comment-only joint edits after the initial commit, plus eight
unrelated updates: 6 co-edits in 14 commits. This deliberately constructed
history demonstrates interpretation, not general precision or recall.

`compatible_related` preserves the call contract, so both signals can be present
while the combined change works. `unrelated` edits `pricing.py` and `banner.py`
together only as a batching habit; history still associates them. The dynamic
case uses `importlib` and `getattr`, which this static projection misses; the
history provides a candidate review point. `not_observed` is never `Clear` or
proof of no dependency.

### Read history and combined evidence

The runner calls the existing `_cg_cochange.cochange_pairs` twice: with the
producer's defaults for selected candidates, and with relaxed thresholds to
show the underlying synthetic counts. It reads default parameters from the
function signature rather than duplicating the calculation. Current defaults
include support 5, minimum probability 0.3, and lift 2. The JSON exposes the
window, commit-size and pair limits, counts, directional probabilities, and
whether each pair passed the default filters.

Only the common-base history is analyzed. The subsequent branches and their
merge are not mixed into the historical evidence. The observed probability
and lift describe this constructed history, not causation or future failures.

`combined.union` means either local candidate set contains this file pair;
`combined.corroborated` means both do. Each case compares one pair. These are
explicit offline set comparisons, not the App's PostgreSQL PR policy. In that
policy, history can corroborate a narrowly suppressed static hub relationship;
other historical partners are separate advisory hints. See the
[implementation inventory](../../docs/ANALYSIS_ASSETS.md).

## A shared, labeled regression benchmark

The same four cases can now be scored against a separate
[review-pair label file](review-labels.json). The question is whether the selected
pair has a functional relationship worth inspecting, **not whether a bug will
occur**. There are three positive pairs and one deliberately unrelated pair.
The dynamic lookup is an unresolved static case; co-change supplies historical
evidence, not proof of its runtime target.

```sh
python3.12 examples/structural-overlap/benchmark.py
python3.12 examples/structural-overlap/benchmark.py \
  --measurements /path/to/NEW-measurements.json > review-pair-scores.json
python3.12 -m unittest discover -s tests -p 'test_structural_overlap_benchmark.py' -v
```

`--git /path/to/git` is supported. The measurements destination must be a new
file. The runner reuses the existing fixture collector and producers; it does
not copy the Co-change formula or add a production detector. Its stable output
is [expected-scores.json](expected-scores.json), generated by a real local run.

| Evidence used as a review candidate | TP | FP | FN | TN | Precision | Recall |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Code graph | 2 | 0 | 1 | 1 | 2/2 | 2/3 |
| Co-change | 2 | 1 | 1 | 0 | 2/3 | 2/3 |
| Either (union) | 3 | 1 | 0 | 0 | 3/4 | 3/3 |
| Both (corroborated) | 1 | 0 | 2 | 1 | 1/1 | 1/3 |

TP/FP/FN/TN count the **four preselected synthetic pairs only**. Precision is
`TP / (TP + FP)` and recall is `TP / (TP + FN)`; a zero denominator is JSON
`null`, not a perfect score. More candidates are not automatically better:
union fills the dynamic miss but retains the incidental-history false positive.
The compatible case is a true review relationship whose combined execution
passes. None of these scores is bug-detection accuracy.

The original demo and its 13 regression tests still enforce their committed
observation matrix. The benchmark calls the collector before that self-check,
so a changed extractor can be measured against the fixed labels rather than
being forced to reproduce an old miss. A proposed improvement must also explain
and update affected regression expectations; do not delete a negative case or
change its label just to improve a score.

`--measurements` separates variable machine measurements from stable scores:
wall time includes worker startup, all four disposable histories, extraction,
synthetic executions and the route/config probes. `child_ru_maxrss` records
`RUSAGE_CHILDREN` after that worker, in bytes on macOS or KiB on Linux. It is
**not aggregate concurrent process-tree peak memory**. The file records Python,
platform, Core commit, dirty state and fixture/scorer/label hashes, without local
absolute paths. Report a clean, pinned checkout for reproducible comparisons;
an uncommitted run is explicitly dirty.

This is a small constructed regression benchmark, not an independent sample of
real repositories. It measures no general precision/recall, Top-K ranking,
reviewer time, vulnerability rediscovery, or production failure reduction.
Parser-level ambiguous symbols need their own labeled cases; the dynamic miss
here is not a calibrated uncertainty score. Timing and RSS vary by machine and
caches. Both the existing demo and scoring boundary tests run in `public-ci`.

To contribute, submit a minimal public/synthetic counterexample, the fixed
versions, expected review relationship with a source-based explanation, and the
actual result using the [contribution guide](../../CONTRIBUTING.md). Never put
undisclosed vulnerabilities or private source in a public Issue.

## Additional API and configuration probes

The report also checks two existing static producers:

- `api_route`: a synthetic Python route definition and a literal TypeScript
  `fetch` URL are paired by `_cg_routes.scan_repo`.
- `config_key`: two Python files reading the same `checkout_fee` key from a
  JSON configuration are paired through the existing graph and adjacency helper.

Both probes are observed in the committed report. They parse source; they do
not execute FastAPI, TypeScript, HTTP requests, or configuration consumers.
They do not establish full language coverage or API compatibility.

## Which implementation is reused

[`demo.py`](demo.py) calls `code_graph_extract.build_graph` and
`cochange_backtest.coupled_pairs` for file-level relationships, `_cg_cochange.cochange_pairs` for history, and the existing
route producer for the route probe. The adjacency helper is the offline
evaluator's coarse approximation, not an execution of the PostgreSQL
open-PR decision pipeline. No new conflict detector or production policy was
added. `hosted_signal` is explicitly `not observed`.

This differs from [the Flask history evaluation](../../docs/OFFLINE_EXAMPLE.md):
that example measures retrospective co-change on a pinned public repository;
this one demonstrates particular constructed changes and their outcomes.
Neither result establishes general accuracy, productivity gains, or merge safety.

## Use the warning in an AI-assisted workflow

A human or coding agent can use the evidence to inspect the named functions
and revisions, preserve compatibility, agree a landing order, and run combined
tests. In the first fixture, retaining a keyword argument or preserving the
function's accepted call forms addresses the observed mismatch. This demo does
not automatically apply either change or control an agent.

The separate [MCP/Codex adapter](https://github.com/RollNuts/zenn-content/tree/89fe0fe12258c827a9e7fc54cb12fc96401018de/examples/core-local-mcp)
can return a small selection of fixed-snapshot metadata to an agent. Its tools
are read-only; current worktree state, other tool permissions, and subsequent
edits must be checked separately. The SDK-only example is model-free; optional
Codex execution uses a logged-in account's model allowance and is not needed
for this local demo.

## Validate and inspect

```sh
python3.12 -m unittest discover -s tests -p 'test_structural_overlap_demo.py' -v
```

Tests use real Git, the existing extractors, the four execution outcomes, the
route/config probes, and a bad-Git failure case. They also verify metadata-only
reporting and reject a forged successful integrated result. Git configuration,
hooks, inherited Git-directory settings, and Python package imports are isolated
for the disposable fixtures. They do not run the PostgreSQL, webhook, hosted,
or full release-gate suites.

The report contains synthetic relative paths, relationship types, and outcomes.
It omits source bodies, diffs, temporary absolute paths, and subprocess traces.
The fixture code itself is visible in `demo.py` so another developer can inspect
and challenge the experiment.

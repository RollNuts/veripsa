## 背景記事の下書き

### Gitがマージできた後に、何を一緒に確認するか

別々のコーディングエージェントへ作業を分けると、一方は関数の定義を、もう一方は呼び出し側を変えることがあります。変更するファイルが違えば、Gitはテキストを問題なくマージできるかもしれません。しかし、それぞれの変更が前提としていた引数やデータの形まで一致するとは限りません。

この接点を、変更した行だけでなく構造から調べたい。それが、今回Veripsa Coreで検証する問いです。作者は[RollNuts](https://github.com/RollNuts)です。目的は、他の開発者が価値を理解し、手元で試し、結果に疑問を持てる技術資産を残すことにあります。

#### 同じエンジンを、小さいGitリポジトリで試す

Coreには既に、ソースから呼び出しやimport、設定、APIなどの関係を取り出す実装があります。今回は別の検出器を作るのではなく、その抽出器と、オフライン評価器が使う粗いファイル間の隣接関係を再利用しました。

デモは一時ディレクトリ内に架空のGitリポジトリを作ります。二つのbranchをそれぞれ実行し、実際にGitでマージした後、組み合わせたPythonも実行します。解析結果だけを見せるのではなく、テキストの統合とプログラムの実行を別の観測として並べます。

```sh
git clone https://github.com/RollNuts/veripsa.git
cd veripsa
python3.12 examples/structural-overlap/demo.py
```

GitとPython 3.12が必要です。clone後のデモには、追加パッケージ、モデルAPI、アカウント、データベースは不要です。デモ内のマージ先は一時リポジトリで、実行者の作業リポジトリを統合しません。

#### 見つかった関係と、実行結果を分ける

デモが照合するケースは次の4つです。すべて合成例で、各branchは単独では実行に成功し、Gitのマージもcleanになります。

| ケース | 構造上の関係 | 統合後の実行 |
| --- | --- | --- |
| 関数の契約を変え、呼び出し側も別に変える | `observed` | `TypeError` |
| 互換性を保って、関連コードを変える | `observed` | 成功 |
| 無関係なファイルを変える | `not_observed` | 成功 |
| 動的な名前解決で呼び出す | `not_observed` | `TypeError` |

最初の例では、構造上の関係が、変更を一緒に読むための手掛かりになります。一方、次の例は「関係があるからバグ」とは言えないことを示します。最後の例では、実行すると壊れるのに、今回の静的な解決では関係が出ません。

つまり、辺が出ることと、変更が間違っていることは別です。辺が出ないことも、安全性の証明にはなりません。Coreの結果を「次に何を確認するか」の材料として使うために、この両側を同じデモへ含めました。

APIルートと設定キーの小さい静的プローブもあります。これらは既存の解析器が合成入力から接点を拾うことを確かめます。アプリのフレームワークを起動して動作を検証するケースとは区別します。

#### 本文を持たず、どこまで判断材料を残すか

Coreは解析時にソース本文を読むことがあります。保存・表示するのは、ファイルパス、シンボル、構造上の関係、PRやcommitの識別情報、判断状態などです。ソース本文やdiff本文を蓄積する設計にはしていません。

本文を除けば情報がなくなる、という意味ではありません。パスや契約名だけでも開発内容が分かる場合があります。今回のデモも、出力する相対パスと証拠の種類を絞り、架空の入力だけを使います。

この境界は[セキュリティ文書](../SECURITY.md#content-free-posture)にあります。現在のheadに判断を結び付け、状態が変われば関係を作り直す設計は[アーキテクチャ](../ARCHITECTURE.md)で説明しています。

#### AIが候補を受け取った後にすること

別repoには、保存済みのCoreのsnapshotを読む[MCPアダプターの実験](https://github.com/RollNuts/zenn-content/tree/89fe0fe12258c827a9e7fc54cb12fc96401018de/examples/core-local-mcp)もあります。公式Tauri例から得た関係をCodex CLIへ問い合わせる実証が記録されています。

SDKだけの手順はモデルを呼びません。任意のCodex手順はログインとモデル利用枠を使うため、今回の無料デモには含めていません。製品版MCPやClaude Codeの常駐設定を、今回導入したという説明でもありません。

候補を受け取ったエージェントは、解析したcommitを確かめ、相手ファイルの前提を読み、互換性を保つ修正や取り込み順を提案し、統合後のテストを実行できます。その行動は、エージェントに別途与えた権限や人間の判断に従います。固定snapshotを問い合わせただけで、編集中のworktreeやmergeの安全性が保証されることはありません。

#### 今回の範囲と、次に確かめたいこと

今回のデモはローカルの構造上の接点を扱います。PostgreSQL上のPR判定処理や、現在稼働するGitHub Checkの検証結果ではありません。ホスト型GitHub Appは停止中で、ホスト由来の結果は`not observed`です。合成例から一般的な検出精度や実利用の時間短縮も算出していません。

別の検証として、[Flaskの固定した公開履歴を使う評価](OFFLINE_EXAMPLE.md)があります。構造上の関係が、過去の同時変更と対応していたかを比較する手順です。小さい合成例、履歴評価、実運用の結果は、それぞれ分けて蓄積します。

次に確かめたいのは、別の公開コードでも、この接点が開発者の確認に役立つかです。同じコマンドと比較条件で他の人が試せることを、その出発点にしました。

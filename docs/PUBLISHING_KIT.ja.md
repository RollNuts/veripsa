## 背景記事の下書き

### Gitコンフリクトを減らしたくて作ったCoreを、検証できる技術資産にする

Veripsa Coreを作り始めた動機は、Gitのコンフリクトが何度も起き、その解消に手間がかかる状況を改善したかったことです。ここから先の開発経緯は、作者[RollNuts](https://github.com/RollNuts)自身が説明した内容です。今回用意する小さい実験の結果とは分けて記録します。

#### 並行するAI開発を見越したが、需要の見え方には時間がかかった

作者は、将来は複数のAIを並行して使う開発が増え、変更同士を調整する必要も増えるだろうと考えていました。ただし、その需要が目に見える形になるまでには、当時の見通しより時間がかかったと振り返っています。これは作者の見通しと経験の説明で、需要の増加率や市場規模を測った結果ではありません。

#### MCPの案も、当時からあった

エージェントから呼び出して使うMCPの案もありました。ただ、その使い方では、エージェントが問い合わせることが入口になります。PRの作成やpushをきっかけに解析を始めるには、そのイベントを受けて処理を起動する役割も必要です。そこでCoreでは、GitHub Appとしてイベントを受信し、並行するPRの状態を更新する構成を選びました。

AppとMCPは、起動するきっかけと、結果を受け取る経路が違います。App側の自動解析も、サービスが稼働し、イベントを正常に受信・処理できることが前提です。現在のホスト型GitHub Appは停止しています。

#### 積極展開を見送ったことと、今の目的

当時はMCPの収益化にも見通しが立たず、ホスト型サービスについてもインフラの運用負担と収益の釣り合いを見通せなかったため、積極的な展開を見送りました。これは過去の検討経緯です。現在は販売や課金導線の構築を目的にせず、技術を公開して検証できる形にすることへ取り組んでいます。

今は、開発の中で得られた実装を技術資産として残し、他の開発者が価値を理解し、手元で試し、検証できる形へ整えたいと考えています。Veripsaという名前だけでなく、RollNutsが何を作り、何を確かめたのかが伝わることを目指します。

開発にはAIを利用しています。作者の実体験として記すのは、コンフリクトに困ったこと、当時の選択や検討経緯、現在の目的です。今回の文書整備やデモの検証にもコーディングエージェントを使い、実行結果を公開コードと照合して示します。作者の説明と、コードや実験から確認できることを区別して記録します。

#### 今、確かめる問い

別々の作業で、一方が関数の定義を、もう一方が呼び出し側を変えるとします。変更するファイルが違えば、Gitはテキストを問題なくマージできるかもしれません。しかし、それぞれの変更が前提としていた引数やデータの形まで一致するとは限りません。

この接点を、変更した行だけでなく構造から調べたとき、何が分かるのか。今回はその問いを、小さい再現例で確かめます。これは、実際の出発点から育った技術を、他の人が確かめられる形へ整える作業です。

#### 同じエンジンを、小さいGitリポジトリで試す

Coreには既に、ソースから呼び出しやimport、設定、APIなどの関係を取り出す実装と、Git履歴から同時変更の組を計算する実装があります。今回は別の検出器を作るのではなく、その抽出器、オフライン評価器が使う粗いファイル間の隣接関係、既存のCo-change producerを再利用しました。

デモは一時ディレクトリ内に架空のGitリポジトリを作ります。二つのbranchをそれぞれ実行し、実際にGitでマージした後、組み合わせたPythonも実行します。解析結果だけを見せるのではなく、テキストの統合とプログラムの実行を別の観測として並べます。

```sh
git clone https://github.com/RollNuts/veripsa.git
cd veripsa
python3.12 examples/structural-overlap/demo.py
```

Git、Python 3.12、POSIXシェルが必要です。macOS／Linux向けの手順で、今回はmacOSで実測し、Windowsでは検証していません。clone後のデモには、追加パッケージ、モデルAPI、アカウント、データベースは不要です。デモ内のマージ先は一時リポジトリで、実行者の作業リポジトリを統合しません。

#### 見つかった関係と、実行結果を分ける

デモが照合するケースは次の4つです。すべて合成例で、各branchは単独では実行に成功し、Gitのマージもcleanになります。コードの静的な構造と、ファイルが一緒に変わった履歴を別々に取り出し、候補集合も比較します。

| ケース | Code graph | Co-change | union | intersection | 統合後の実行 |
| --- | --- | --- | --- | --- | --- |
| 関数の契約を変える／履歴1commit | `observed` | `not_observed` | `observed` | `not_observed` | `TypeError` |
| 互換性を保って、関連コードを変える | `observed` | `observed` | `observed` | `observed` | 成功 |
| 無関係なファイルを同じcommitで更新する | `not_observed` | `observed` | `observed` | `not_observed` | 成功 |
| 動的な名前解決で呼び出す | `not_observed` | `observed` | `observed` | `not_observed` | `TypeError` |

`union`はどちらかで観測された候補、`intersection`は両方で観測された候補です。出力JSONでは、共通集合を`combined.corroborated`と表記しています。この集合の比較はオフラインの実験で、AppのPR判定規則ではありません。

最初の例では、構造上の関係が、変更を一緒に読むための手掛かりになります。履歴は1commitしかないため、Co-changeの共同変更回数の既定条件に届きません。残りの3例には、14commit中6回、対象2ファイルを一緒に変更する履歴を作りました。今回使う既存producerの既定条件は、共同変更回数`co >= 5`、方向付き確率の大きい方である`strength >= 0.3`、`lift >= 2.0`です。

履歴が動的参照の候補を補う例もあれば、無関係なファイルを偶然一緒に更新したために候補へ入る例もあります。Co-changeが示すのは共変更で、因果関係や将来の故障ではありません。unionではこの4例すべてが候補になり、intersectionでは失敗する2例をどちらも落とします。関係を足すことや両方に絞ることを、そのまま一般的な精度向上とは説明できません。

辺や履歴の候補が出ることと、変更が間違っていることは別です。出ないことも安全性の証明にはなりません。[期待出力](../examples/structural-overlap/expected-output.json)で、同じ条件と値を追えます。

APIルートと設定キーの小さい静的プローブもあります。これらは既存の解析器が合成入力から接点を拾うことを確かめます。アプリのフレームワークを起動して動作を検証するケースとは区別します。

#### 本文を持たず、どこまで判断材料を残すか

Coreは解析時にソース本文を読むことがあります。保存・表示するのは、ファイルパス、シンボル、構造上の関係、PRやcommitの識別情報、判断状態などです。ソース本文やdiff本文を蓄積する設計にはしていません。

本文を除けば情報がなくなる、という意味ではありません。パスや契約名だけでも開発内容が分かる場合があります。今回のデモも、出力する相対パスと証拠の種類を絞り、架空の入力だけを使います。

この境界は[セキュリティ文書](../SECURITY.md#content-free-posture)にあります。現在のheadに判断を結び付け、状態が変われば関係を作り直す設計は[アーキテクチャ](../ARCHITECTURE.md)で説明しています。

#### Code graph、Co-change、状態の保存を個別に確かめる

開発を進める中で、コードの構造を取り出すCode graph、過去の同時変更を比較するCo-change、イベントや判断状態を保持する仕組みが蓄積しました。それらは今、何に使え、どこまで確かめられるのかを調べる対象です。

今回の合成デモは、同じ変更ペアについて、Code graphとCo-change、候補集合のunionとintersectionを比較する例です。既存の[Flask評価](OFFLINE_EXAMPLE.md)は、構造と過去の同時変更との対応を調べる別の例です。既存コードの入口、今回の検証範囲、今後の使い方は[実装資産の棚卸し](ANALYSIS_ASSETS.md)へまとめています。

状態の保存も、Appの処理を支える独立した確認対象です。DBにはイベントやexact head、人間のACKなどを継続して扱う役割があります。今回の手軽なローカルデモがDBを使わないことは、AppからDBを消すという方針ではありません。DBを含む検証は、隔離した環境の条件と結果を別に示します。 App側には、履歴を別枠で知らせるadvisoryと、広く参照されるファイル（hub）を抑制して`unknown`になった一部の静的関係を、履歴で裏付けるSQL処理があります。一般的なunionをそのままPR判定へ使う実装とは異なります。[構造と履歴の関係](ANALYSIS_ASSETS.md#static-and-historical-evidence-complement-each-other)で、その違いを確認できます。

#### AIが候補を受け取った後にすること

別repoには、保存済みのCoreのsnapshotを読む[MCPアダプターの実験](https://github.com/RollNuts/zenn-content/tree/89fe0fe12258c827a9e7fc54cb12fc96401018de/examples/core-local-mcp)もあります。公式Tauri例から得た関係をCodex CLIへ問い合わせる実証が記録されています。

SDKだけの手順はモデルを呼びません。任意のCodex手順はログインとモデル利用枠を使うため、今回の無料デモには含めていません。製品版MCPやClaude Codeの常駐設定を、今回導入したという説明でもありません。

候補を受け取ったエージェントは、解析したcommitを確かめ、相手ファイルの前提を読み、互換性を保つ修正や取り込み順を提案し、統合後のテストを実行できます。その行動は、エージェントに別途与えた権限や人間の判断に従います。固定snapshotを問い合わせただけで、編集中のworktreeやmergeの安全性が保証されることはありません。

#### 今回の範囲と、次に確かめたいこと

今回のデモはローカルの構造上の接点を扱います。PostgreSQL上のPR判定処理や、現在稼働するGitHub Checkの検証結果ではありません。ホスト型GitHub Appは停止中で、ホスト由来の結果は`not observed`です。合成例から一般的な検出精度や実利用の時間短縮も算出していません。

別の検証として、[Flaskの固定した公開履歴を使う評価](OFFLINE_EXAMPLE.md)があります。構造上の関係が、過去の同時変更と対応していたかを比較する手順です。小さい合成例、履歴評価、実運用の結果は、それぞれ分けて蓄積します。

次に確かめたいのは、別の公開コードでも、この接点が開発者の確認に役立つかです。同じコマンドと比較条件で他の人が試せることを、その出発点にしました。
